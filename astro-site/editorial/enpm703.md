# ENPM703 시리즈 편집 지침 제안

검토용 초안. ENPM703의 개념 이해와 구현을 연결하기 위한 편집 원칙을 제안한다.

## 글의 목적과 독자
- 신경망을 처음 배우거나 오래 쉬었다가 돌아온 학생이 글 안에서 개념을 이해하고, 관련 코드를 읽고, 필요한 작은 계산을 직접 수행할 수 있게 쓴다.
- 독립적인 블로그 글로 쓴다. 작성자와 AI의 대화, 이해하게 된 개인적 순간, 자료를 모으고 대조한 과정은 설명에 넣지 않는다.
- 글을 읽고 할 수 있어야 하는 일을 구체적으로 정한다. 예: 배열 shape 설명하기, gradient 유도하기, 코드 한 블록 구현하기, 학습 곡선 해석하기.
- 사용자가 지정한 범위를 우선한다. 다음 단원을 이해하는 데 필요한 연결만 설명하고, 아직 요청하지 않은 과제 전체나 다른 모델로 확장하지 않는다.

## 서문과 학습 흐름
- 이 개념이 어떤 문제를 해결하는지, 앞에서 배운 계산의 무엇을 확장하는지 설명한다.
- 기본 흐름은 문제와 작은 예 → 개념도 → 스칼라 계산 → 배열·수식 → 코드 → 결과 해석으로 잡는다. 모든 절에서 같은 틀을 기계적으로 반복하지는 않는다.
- 낯선 용어와 기호는 처음 등장할 때 뜻과 역할을 설명한다. 수식이 등장하기 전에 무엇을 계산하려는지 말한다.
- 출처·검증·편집 판단은 서문에 나열하지 않는다. 글 끝의 참고 자료도 독자가 다시 찾을 자료명과 필요한 단원만 간결하게 적는다.

## 수식과 배열
- Sample, feature, neuron, class, batch를 구분한다. N, D, H, C 등의 의미를 먼저 정하고 배열 축과 shape를 함께 쓴다.
- Sample을 행으로 두는지 열로 두는지 명시하고 본문·그림·코드에서 같은 convention을 유지한다.
- Forward 값, loss, 해당 값에 대한 gradient를 구분한다. `dx`는 x 자체나 업데이트된 값이 아니라 최종 loss의 x에 대한 미분임을 설명한다.
- Backward는 upstream × local derivative와 같은 변수에 도착하는 경로의 합에서 유도한다. Transpose 위치를 shape 맞추기만으로 정당화하지 않는다.
- Batch 평균의 1/N, 합산 축, broadcasting과 reshape의 의미를 설명한다. Regularization의 계수는 loss와 gradient 양쪽에서 일치시킨다.
- Score와 probability, parameter와 hyperparameter, gradient 계산과 optimizer update, training과 inference를 구분한다.
- 작은 숫자 예제를 먼저 계산하고 일반식으로 확장한다. 근사·미분 불가능점·수치 안정성에 관한 조건은 해당 계산에 필요한 만큼 설명한다.

## 코드와 과제 연결
- 현재 설명을 이해하는 데 필요한 코드만 해당 절에 넣는다. 과제 전체 파일, 무관한 setup·튜닝 loop·긴 학습 로그는 복사하지 않는다.
- 코드가 함수 전체인지 메서드 일부인지 구분하고, 필요한 import·입력·출력·shape·주변 문맥을 설명한다.
- 코드의 변수명과 수식 기호를 대응시킨다. 예: `dout = ∂L/∂Y`, `dw = ∂L/∂W`.
- NumPy의 `@`, 원소별 곱, broadcasting, `axis`, mask, cache처럼 계산 의미를 바꾸는 부분을 설명한다. 모든 줄을 문법적으로 반복 해설하지 않는다.
- Loss·gradient를 계산하는 함수와 학습을 반복하는 Solver·optimizer의 역할을 구분한다. 실행 순서와 어디에 결과를 반환하는지 보여준다.
- 구현의 연결에 필요한 이유를 설명한다. 예: cache에 왜 입력을 저장하는지, 평균을 왜 두 번 내면 안 되는지, weight를 언제 갱신하는지.
- 특정 코드나 출력의 동작을 설명할 때 실제 확인한 자료에 맞춘다. 확인하지 않은 구현·학습 결과를 만들어 내지 않는다.

## 그림과 결과 해석
- 뉴런 연결, 데이터·gradient의 흐름, 합산 축, 정규화 축처럼 글만으로 놓치기 쉬운 구조에 개념도를 넣는다.
- 그림은 해당 설명 바로 옆에 둔다. 장식용 그림은 넣지 않는다.
- 노드와 선의 의미, 화살표 방향, sample 수와 layer 수를 명확히 한다. 단순화한 neuron 수나 생략한 bias 연결은 필요한 경우 본문에서 설명한다.
- 코드 변수와 수학 기호는 그림에서도 일관되게 쓴다. 긴 설명은 그림 밖에 두고, 색만으로 forward와 backward를 구분하지 않는다.
- 수치 예제의 부호·계수·합산 결과를 확인한다. 그림의 숫자는 바로 옆 수식·설명과 일치시킨다.
- 학습 결과를 다룰 때 loss, training accuracy, validation accuracy가 각각 무엇을 보여주는지 설명한다. 검증 성능과 테스트 성능, 적합 능력과 일반화 능력을 구분한다.
- 실험 조건은 결과 해석에 필요한 것만 남긴다. 기록된 한 번의 좋은 결과를 항상 성립하는 규칙이나 최적 설정으로 표현하지 않는다.

## 확인 문제와 해설
- 각 문제 바로 아래에 기본적으로 닫힌 「정답과 해설 펼치기」를 둔다. 기존 `review-answer`와 테마 색상을 사용한다.
- 용어 암기 외에 shape 예상, 작은 forward·backward 계산, 잘못된 코드 수정, 학습 결과 해석을 글의 범위 안에서 섞는다.
- 해설은 답만 적지 않고 필요한 계산·합산 축·코드 대응과 흔한 오해를 설명한다. 해설을 열어야 답이 드러나게 배치한다.
- 핵심 개념을 처음 설명하는 본문이나 학습에 꼭 필요한 구현을 접힌 해설 안에만 숨기지 않는다.

## 표기와 출처
- 한글 조사·괄호·수식 옆의 강조는 `<strong>…</strong>`로 쓴다. 코드 밖에서 `**`가 문자로 노출되지 않는지 생성된 본문을 확인한다.
- 강의·과제 내용을 참고하되 설명은 독자가 이해할 수 있는 완결된 문장으로 쓴다. 직접 인용은 실제 확인한 원문만 사용하고 필요한 출처를 붙인다.
- 내부 파일 경로, 개인 노트 제목, 대조·재구성·검산·재실행 내역을 독자용 출처란에 나열하지 않는다. 풀이에 필요한 가정과 구현 조건은 해당 설명에서 밝힌다.

## 검증과 완료 보고
- 작업 전에 완료 조건과 변경에 맞는 검증 범위를 짧게 정한다. 글 수정은 빌드·수식·이미지 링크·접기 구조 등 영향을 받은 부분만 확인한다.
- 계산·코드가 바뀌면 작은 예제나 필요한 gradient check로 확인한다. 코드 발췌를 넣었다는 이유만으로 전체 데이터 학습을 재실행하지 않는다.
- 기존 검사 통과 뒤 새 변경·실패·미해결 문제가 없으면 같은 검사를 반복하지 않는다. 같은 문제를 두 번 수정해도 반복되면 원인과 접근법을 재검토한다.
- 브라우저 순회·스크린샷 수집·화면 폭·테마별 육안 검증은 별도 요청이 없으면 사용자에게 맡긴다.
- 구현, 빌드, 배포 반영, 육안 확인, 실제 코드 실행을 구분해 보고한다. 사용자에게 확인할 절·그림·버튼과 기대되는 모습을 구체적으로 안내한다.

## 사이트 공통 구성
- 본문 자간·코드와 수식의 간격, 페이지당 목록 수와 시리즈 정렬은 기존 사이트 공통 설정을 따른다. 글마다 별도 스타일을 누적하지 않는다.
- 이 제안을 확정하면 ENPM703의 편집 기준 문서로 관리하고 이후 지시를 여기에 반영한다.
